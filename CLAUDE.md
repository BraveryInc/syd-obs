# CLAUDE.md

This file provides guidance when working with code in this repository.

## What This Is

**Syd** is a multi-tool security analysis platform with a Tkinter GUI. It integrates Nmap, BloodHound, Volatility, and other tools with a local LLM (Qwen 2.5 14B via llama-cpp) and a RAG engine for context-aware analysis.

**Contribution boundary for this repo:**
- The **LLM, RAG engine, and analysis logic** are owned by the main author. Do not modify `BloodHoundAnalyzer`, `VolatilityAnalyzer`, the RAG engine, or the `create_chat_completion` call in `_run_llm_analysis`.
- **`obsidian_export.py`** is the Obsidian output contribution layer — add features here freely.
- **`syd.py`** may be touched minimally to wire new export functions into the UI, following the existing ReportBuilderPage pattern.

## obsidian_export.py — Overview

This module is the presentation layer for Obsidian output. It takes analysis text and structured data already generated by Syd's LLM and renders it into Obsidian markdown notes + a Canvas visualization.

### Functions syd.py calls (signatures must not change)

| Function | Called from | Purpose |
|----------|-------------|---------|
| `syd_services_to_scan_data(services, xml_path, scan_name, nmap_args)` | ReportBuilderPage | Converts Syd's flat services list to scan_data dict |
| `build_analysis_prompt(scan_data)` | ReportBuilderPage._run_llm_analysis | Builds the LLM user-message prompt for Nmap data |
| `export_to_obsidian(vault_dir, scan_data, scan_name, analysis_text, model_name, canvas_name)` | ReportBuilderPage._export_worker | Full Nmap export pipeline |

### New functions (not yet wired in syd.py — hooks marked with comments)

| Function | Purpose |
|----------|---------|
| `export_bloodhound_to_obsidian(vault_dir, report_text, vulnerabilities, scan_name, model_name)` | BloodHound export — takes BloodHoundAnalyzer output, writes host notes + scan note + canvas |
| `export_volatility_to_obsidian(vault_dir, analysis_text, target_host, scan_name, model_name)` | Volatility export — takes analysis text, writes host note + scan note + canvas |

Hook comments in syd.py mark the exact call sites (search for `=== OBSIDIAN EXPORT HOOK ===`).

## Syncing from mAIpper

obsidian_export.py is kept in sync with mAIpper — it implements the same canvas layout and host note format. When mAIpper releases a new version, relevant improvements should be ported here.

**Last synced from:** mAIpper-v0.7

### What to check on each sync

Before syncing, diff mAIpper's relevant functions against obsidian_export.py equivalents:

| mAIpper function | obsidian_export.py equivalent | Notes |
|-----------------|-------------------------------|-------|
| `build_canvas` | `build_canvas` | Canvas layout, node types, edge routing |
| `_write_host_note` | `_write_host_note` | Frontmatter merge logic, section preservation |
| `_build_campaign_overview` | `_build_campaign_overview` | Stats aggregation |
| `_build_next_steps` | `_build_next_steps` | Section extraction from AI text |
| `build_ollama_prompt` | `build_analysis_prompt` | **Signature differs** — obsidian_export uses a single `scan_data` arg; mAIpper passes additional context. Port the prompt body/instructions, not the signature. |
| `get_port_hints` | `_render_port_hints` | Port hint text — keep in sync |
| `get_tags_from_ports` | `get_tags_from_ports` | Tag inference logic |
| `STATUS_COLORS` | `STATUS_COLORS` | Canvas color map |

### What NOT to port

- **Ollama integration** (`ollama_chat`, `--ollama-url`, `--model`, temperature, two-pass Nessus) — Syd has its own LLM via llama-cpp; do not add Ollama calls.
- **Validation layer** (`validate_ai_output`, `--skip-validation`, Validation Warnings sections) — the main author owns output quality.
- **CLI argument parsing** (`argparse`) — mAIpper is a CLI tool; syd is a GUI app.
- **Nessus/Burp parsers** — mAIpper parses these itself; Syd may get this data through different paths.

### What to port

- Canvas layout changes (new nodes, edge routing, layout constants)
- Host note format changes (new frontmatter keys, new body sections)
- `build_analysis_prompt` improvements (grounding rules, AD detection, output format sections)
- New helper functions that are pure rendering logic (no LLM calls, no CLI args)
- `export_bloodhound_to_obsidian` / `export_volatility_to_obsidian` — these are obsidian_export.py-native and have no mAIpper equivalent, but keep them consistent with the overall note/canvas architecture

## Canvas Layout

```
[ Campaign Overview — stats + key findings ]
              ↓
  [ Priority Targets — ranked attack order ]
       ↓           ↓           ↓
[ Scan Card ]  [ Scan Card ]  [ Scan Card ]
     ↓  ↓              ↓  ↓
┌── 10.10.10.0/24 ──┐  ┌── 192.168.1.0/24 ──┐
│ host  host        │  │ host  host          │
└───────────────────┘  └─────────────────────┘
[ Next Steps ]
```

Scan cards can represent Nmap, BloodHound, or Volatility scans — they all appear on the same canvas, connected to the host cards they produced. Use `_read_existing_scan_host_map(vault_dir)` to read the current state before rebuilding so nothing gets dropped.

## Host Note Frontmatter

```yaml
---
ip: 10.10.10.5
hostnames: ["dc01.domain.local"]
status: not-started        # not-started / in-progress / done / exploited / blocked
tags: ["smb", "kerberos", "ldap", "domain-controller", "bloodhound", "memory-forensics"]
sources: ["InternalScan - Nmap", "BloodHound", "Volatility"]
nessus_max_severity: 4     # if present, drives canvas card color when status = not-started
volatility_max_severity: "critical"   # if present, set by Volatility export
---
```

## Key Conventions

- `_safe_filename()` strips illegal Obsidian/Windows filename characters.
- Obsidian links use `[[Hosts/<stem>|display]]` syntax — no `.md` extension.
- Canvas node IDs use `_stable_id(semantic_key)` (MD5 hash) — stable across re-exports.
- Canvas file node paths are relative to vault root, forward slashes only.
- `OPERATOR_NOTES_SENTINEL = "## Operator Notes"` — always the last section; always preserved on re-export.
- New tool-specific sections (e.g., `## BloodHound Findings`, `## Volatility Analysis`) go between the auto-generated content and the Operator Notes sentinel.
